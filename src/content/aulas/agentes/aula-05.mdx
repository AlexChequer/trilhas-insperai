Nas quatro aulas anteriores o agente foi construído na unha: o formato de tool call foi inventado por nós, o parser é uma expressão regular nossa, o registro de ferramentas é um dicionário Python nosso, e a lista que o modelo lê foi digitada à mão no system prompt.

Funciona — e nada disso é o seu problema de verdade. Inventar um formato de tool call não resolve nada para ninguém: é trabalho de encanamento, refeito igual por toda equipe que monta um agente. Esta aula troca esse encanamento por um protocolo pronto, e a razão de ela vir só agora é que **jogar fora um código que você não escreveu não ensina nada.** Tendo escrito o parser, dá para avaliar o que o protocolo faz por você.

## O problema: cada um inventava o seu

Nossa convenção foi `<tool_call>{...}</tool_call>`. A OpenAI usou outra, a Anthropic outra, cada framework de agente mais uma. Cada combinação de modelo, framework e ferramenta virava um adaptador, e uma ferramenta escrita para um agente não servia para nenhum outro.

O <Termo id="mcp">MCP</Termo> — Model Context Protocol, aberto, criado pela Anthropic em 2024 — padroniza essa conversa. A analogia que pegou é o USB-C: um conector só, no lugar de um por fabricante. A arquitetura tem três papéis:

- **Servidor**: expõe ferramentas e dados de um domínio. Um servidor para o Google Drive, um para o seu banco de dados, um para as ferramentas da entidade.
- **Cliente**: conecta-se a servidores, descobre o que existe neles e executa o que o modelo pedir.
- **Host**: a aplicação onde o modelo roda — o Claude Desktop, o seu agente, uma IDE.

A separação entre servidor e cliente é o que faz a diferença. O servidor não sabe qual modelo está do outro lado, e o cliente não sabe o que as ferramentas fazem. Nenhum dos dois precisa saber, e é por isso que ambos viram reaproveitáveis.

## O servidor: uma função com um decorador

Do lado do <Termo id="servidor-mcp">servidor</Termo>, expor uma ferramenta é escrever a função e decorá-la:

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("Insper AI Agent Tools")


@mcp.tool()
def calculadora(expressao: str) -> str:
    """Avalia uma expressão matemática e devolve o resultado.
    Suporta + - * / ** e funções do módulo math.

    Exemplos:
        calculadora("15 * 23")        → "345"
        calculadora("math.sqrt(144)") → "12.0"
    """
    ...
```

Repare no que **não** está ali. Não há registro num dicionário, não há descrição duplicada num system prompt, não há esquema de argumentos escrito à mão. O decorador lê a assinatura da função — o nome, os tipos dos parâmetros — e a docstring, e monta o esquema sozinho.

Essa é a mudança prática mais importante: a docstring **deixa de ser documentação para humano e passa a ser o texto que o modelo lê para decidir se usa a ferramenta.** Vale o mesmo cuidado da Aula 3 — dizer em que situações usar, e não só o que a função faz.

Além de ferramentas, um servidor pode expor <Termo id="resource">resources</Termo>: dados que o cliente pode ler e colocar no contexto, identificados por uma URI.

```python
@mcp.resource("insperai://trilhas")
def trilhas_disponiveis() -> str:
    """As trilhas abertas no semestre atual."""
    return json.dumps({...}, ensure_ascii=False)
```

A diferença entre os dois é de papel: **ferramenta faz, resource informa.** Ferramenta é chamada pelo modelo quando ele decide; resource é lido pela aplicação e colocado no contexto, mais parecido com abrir um arquivo do que com executar uma ação.

## O cliente descobre em vez de supor

Do lado do <Termo id="cliente-mcp">cliente</Termo> está a peça que a versão artesanal não tinha: a <Termo id="descoberta-de-ferramentas">descoberta de ferramentas</Termo>. Ao conectar, ele pergunta ao servidor o que existe lá, e recebe nome, descrição e esquema de argumentos de cada ferramenta.

```python
await session.initialize()
resposta = await session.list_tools()

ferramentas = [
    {"name": t.name, "description": t.description, "input_schema": t.inputSchema}
    for t in resposta.tools
]
```

Em nenhum lugar desse código aparece a palavra "calculadora". O cliente serve para qualquer servidor MCP, inclusive os que ainda não foram escritos.

<Caixa tipo="erro">
O MCP **não** faz o modelo chamar ferramentas. Ele padroniza como a ferramenta é anunciada, pedida e respondida. Quem decide chamar continua sendo o modelo, gerando tokens, exatamente como na Aula 1 — a diferença é que um modelo grande e ajustado para uso de ferramentas erra muito menos o formato, e que a API já entrega o pedido como bloco estruturado em vez de texto para você parsear.
</Caixa>

## O que se ganha, medido em edições

A forma mais honesta de avaliar o protocolo é fazer a mesma tarefa nos dois mundos. **Aperte o botão** e acrescente a ferramenta nova dos dois lados.

Três edições contra uma, e vale insistir no caso do meio: marcar as duas primeiras edições do lado manual e esquecer a terceira produz o pior desfecho possível. A função existe, o executor a conhece, e **o modelo nunca vai pedir por ela** — porque, na versão manual, o que o modelo sabe é o que alguém digitou no system prompt. Nenhum erro é levantado, nada quebra, e você descobre semanas depois reparando que o agente nunca usa aquela ferramenta.

O problema de fundo é duplicação: a mesma informação — o nome da ferramenta, o que ela faz, que argumentos aceita — vive em três lugares que precisam ficar em sincronia para sempre. No MCP existe uma fonte só, a função decorada, e o cliente pergunta em vez de supor.

Resumindo o que muda de um lado para o outro:

- **O formato do pedido**: era nosso, virou do protocolo.
- **O <Termo id="parser">parser</Termo>**: era uma regex mais um `JSON.parse` mais quatro validações; virou `session.call_tool(nome, args)`.
- **A lista de ferramentas**: era texto digitado no prompt; virou resposta de `tools/list`.
- **A interoperabilidade**: era zero — as ferramentas só funcionavam no nosso código; virou qualquer cliente MCP.

E o que **não** muda:

- O <Termo id="loop-de-agente">laço do agente</Termo> é o mesmo: pedir, executar, devolver, responder.
- A execução acontece no mesmo lugar de sempre: uma função, numa máquina, com as permissões dela.
- Descrição ruim continua produzindo escolha ruim de ferramenta.
- Resultado de ferramenta continua ocupando contexto, e o contexto continua finito. Tudo o que a Aula 4 diz continua valendo.

<Pergunta pergunta="Se o MCP resolve tanta coisa, por que a trilha gastou três aulas construindo isso à mão?">
Porque quem só viu a versão pronta não sabe o que está sendo abstraído — e abstração que você não entende vira caixa-preta assim que quebra. Sabendo que existe um parser embaixo, um JSON malformado deixa de ser mistério. Sabendo que a descrição da ferramenta é o que embasa a escolha do modelo, uma docstring preguiçosa deixa de parecer detalhe. E sabendo que tudo — pedido, resultado, resposta — vira texto no mesmo contexto, o custo de um agente com quarenta ferramentas deixa de ser surpresa. O protocolo poupa o encanamento, não o entendimento.
</Pergunta>

## Um servidor, vários clientes

A consequência prática mais visível da padronização é que o mesmo `mcp_server.py` que o seu agente usa pode ser plugado no Claude Desktop, sem uma linha a mais:

```json
{
  "mcpServers": {
    "insper-ai-tools": {
      "command": "python",
      "args": ["/caminho/completo/para/mcp_server.py"]
    }
  }
}
```

Reiniciado o aplicativo, o Claude passa a poder chamar as suas ferramentas na interface normal de conversa. Você escreveu um servidor; ganhou dois clientes.

É isso que "protocolo" quer dizer na prática, e é a diferença entre escrever uma integração e escrever um adaptador para cada par de coisas que precisam conversar.

<Caixa tipo="atencao">
Padronizar o transporte **não** padroniza a confiança. Um servidor MCP é um processo que roda com as permissões de quem o iniciou: instalar um servidor de terceiros é dar a ele acesso àquela máquina, e as ferramentas que ele anuncia — nome e descrição — entram no contexto do modelo como texto, o que é uma porta de entrada para injection vinda de fora. Vale a mesma régua de instalar uma dependência qualquer: leia o que você está rodando, e dê ao servidor o mínimo de acesso de que ele precisa.
</Caixa>
