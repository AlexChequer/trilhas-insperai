Na Aula 1, o modelo tinha uma variável só: previsão a partir da metragem. É ótimo para aprender, mas ninguém prevê preço de imóvel só com metragem — entram quartos, idade, bairro, andar. Esta aula tem um tema único: **o vetor de entrada pode ter o que você quiser dentro**. E, surpreendentemente, quase nada do algoritmo muda para acomodar isso.

## Mais de uma feature

Cada informação de entrada é uma **feature**. Com várias delas, o modelo vira uma soma:

$$
\text{previsão} = w_1 x_1 + w_2 x_2 + \dots + w_n x_n + b
$$

<Simbolos
  itens={[
    { simbolo: "$x_i$", significado: "a i-ésima feature do imóvel — $x_1$ metragem, $x_2$ número de quartos, $x_3$ idade…" },
    { simbolo: "$w_i$", significado: "o peso da feature $i$: quanto o preço muda quando ela sobe uma unidade e as outras ficam paradas" },
    { simbolo: "$n$", significado: "quantas features o modelo usa" },
    { simbolo: "$b$", significado: "o mesmo deslocamento da Aula 1 — não pertence a nenhuma feature" },
  ]}
/>

Escrever tudo por extenso não escala — imagine com 200 features. Então empacota-se as features num **vetor** $\mathbf{x}$ e os pesos num vetor $\mathbf{w}$, e a soma inteira vira um <Termo id="produto-escalar">produto escalar</Termo>:

$$
\text{previsão} = \mathbf{w} \cdot \mathbf{x} + b
$$

<Simbolos
  itens={[
    { simbolo: "$\\mathbf{x}$", significado: "o vetor de features de um imóvel: $(x_1, x_2, \\dots, x_n)$" },
    { simbolo: "$\\mathbf{w}$", significado: "o vetor de pesos, um para cada feature — o que o modelo aprende" },
    { simbolo: "$\\mathbf{w} \\cdot \\mathbf{x}$", significado: "multiplica cada peso pela sua feature e soma tudo: exatamente a linha de cima, escrita curto" },
  ]}
/>

Repare que é a **mesma** regressão da Aula 1 — a mesma ideia de ajustar pesos para minimizar o custo, o mesmo gradient descent. A única diferença é que $\mathbf{x}$ agora é um vetor em vez de um número. Guarde essa notação vetorial com carinho: **sem ela, a Aula 5 (redes neurais) vira um muro**, porque uma rede nada mais é do que muitos desses produtos escalares empilhados.

## Feature engineering: escolher o que entra

Se o vetor pode ter o que você quiser, a pergunta passa a ser: o que colocar nele? Isso se chama **feature engineering**, e é onde mora boa parte do julgamento de um projeto de ML.

- Uma boa feature **carrega informação** sobre o que você quer prever. Metragem ajuda a prever preço; a cor da porta, não.
- Às vezes a **combinação** de features é melhor que as partes: área é comprimento vezes largura, e a área explica preço melhor do que os dois lados soltos.
- Às vezes **transformar** uma feature ajuda: o log da renda costuma funcionar melhor que a renda crua, porque comprime a cauda dos muito ricos.
- E cuidado: uma feature ruim **não é neutra** — ela adiciona ruído e pode atrapalhar o treino.

<Caixa tipo="erro">
Mais features **não** é sempre melhor. Cada feature sem informação dá ao modelo mais uma maneira de se ajustar ao ruído dos dados de treino, além de exigir mais exemplos para que os pesos se estabilizem. Feature entra por merecimento, não por disponibilidade.
</Caixa>

## Regressão polinomial

E se a relação não for uma reta, mas uma curva? Aqui está o truque mais elegante da aula: você **cria features novas** a partir das que tem. Se tem $x$, crie também $x^2$, $x^3$, e por aí vai. Aí é só rodar a **mesma** regressão linear sobre esse conjunto ampliado.

O resultado é uma curva, mas — e essa é a sacada que faz a ficha cair — você **não mudou o algoritmo**, só mudou a entrada. Por isso "linear" se refere aos **parâmetros** (os pesos entram de forma linear), não à forma do gráfico. Regressão polinomial é <Termo id="feature-engineering">feature engineering</Termo>, não um método novo.

<Pergunta pergunta="Se o gráfico virou uma curva, em que sentido o modelo ainda é “linear”?">
No sentido de como os **parâmetros** entram na conta. Com as features $x$, $x^2$ e $x^3$, a previsão é $w_1 x + w_2 x^2 + w_3 x^3 + b$: cada peso multiplica a sua feature e as parcelas são somadas. Nenhum peso aparece elevado a algo, multiplicado por outro peso ou dentro de uma função.

Quem é curvo é o **$x$**, não o $w$ — e, do ponto de vista do treino, $x^2$ é só mais uma coluna de números que chegou pronta. O algoritmo nem fica sabendo que ela nasceu de outra.
</Pergunta>

Mas há um perigo. **Aumente o grau do polinômio** abaixo e observe: com grau baixo, a curva é simples demais e passa longe dos pontos (isso é **underfitting**). Com grau alto, ela se contorce para tocar cada ponto:

<VizEmbed titulo="arraste o slider de grau, de 1 a 15">
  <GrauPolinomio />
</VizEmbed>

No **grau 15**, a curva passa por todos os pontos e o erro de treino vai a zero. Parece perfeito — mas ela decorou o **ruído**, não a tendência. Numa metragem nova, ela chuta qualquer coisa. Guarde essa imagem: é o retrato do <Termo id="overfitting">overfitting</Termo>, e ela volta com esse nome na Aula 7.

O grau, aliás, é mais um **hiperparâmetro**: você escolhe antes de treinar, o modelo não descobre sozinho. E, como o learning rate da Aula 1, ele tem um ponto certo entre dois extremos ruins.

<Caixa tipo="erro">
Regressão polinomial **não** é um algoritmo diferente. É a mesma regressão linear rodando sobre features que você fabricou. Quem trata os dois como métodos distintos acaba procurando uma biblioteca nova quando bastava acrescentar colunas à entrada.
</Caixa>

## A escala atrapalha o treino

Agora um problema traiçoeiro que só aparece com várias <Termo id="feature">features</Termo>. Metragem vai de 30 a 500; número de quartos, de 1 a 5. São escalas completamente diferentes, e o <Termo id="gradient-descent">gradient descent</Termo> sente isso.

Lembra da tigela de custo da Aula 1? Com features de escalas parecidas, ela é redonda, e a bola rola direto para o fundo. Com escalas muito diferentes, a tigela vira um **vale comprido e estreito** — íngreme numa direção, quase plano na outra. O gradiente aponta forte na direção íngreme e fraco na plana, então a bola **ziguezagueia**: bate de um lado a outro do vale enquanto se arrasta devagar rumo ao fundo. Ela chega, mas leva muito mais passos.

**Ligue e desligue a normalização** e veja o caminho mudar (o painel conta os passos até o fundo):

<VizEmbed titulo="alterne entre com e sem normalização">
  <NormalizacaoZigzag />
</VizEmbed>

Pior ainda: se você criou $x^3$ na regressão polinomial, a escala daquela feature explodiu, e o problema fica bem mais grave.

## Pôr tudo na mesma escala

A solução é deixar as features comparáveis, com uma de duas técnicas:

- <Termo id="normalizacao">**Normalização**</Termo>: espreme cada feature para o intervalo de 0 a 1.
- **Padronização**: recentra cada feature para ter **média 0 e desvio 1**.

As duas resolvem o vale esticado; a padronização costuma ser a escolha padrão. Veja o efeito: no eixo real, a metragem se espalha e os quartos viram um risquinho perto do zero — incomparáveis. **Padronize** e as duas passam a ocupar a mesma faixa:

</VizEmbed>

<Caixa tipo="erro" titulo="Erro comum — e caro">
Calcule a média e o desvio da escala usando **só os dados de treino**, e depois aplique esses mesmos números ao teste. Se você calcula sobre o conjunto inteiro, informação do teste vaza para dentro do treino e você passa a se enganar sobre o quão bom o modelo é. O assunto volta com todo o rigor na Aula 7.
</Caixa>
